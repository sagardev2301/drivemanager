## Step 3 — Wire the fetched designs to the live Supabase backend

Build a mobile-first web app called **DriveManager** for a driving school's daily operations (customer enrollment, class attendance, payments), using the Stitch designs from Step 1 as the actual screens, wired to real data.

**Backend is already set up in Supabase — connect to it via the Supabase MCP, project ref `oelafqskkbmqqkxphvoe`.** Before writing any UI code, introspect the actual schema (tables: `customers`, `classes`, `payments`, and the view `customer_summary`) rather than assuming field names — use what's really there.

Key things to know about the schema:
- `customers`: identity + package info (full_name, phone_number, enrollment_date, package_classes, total_fee, course_status enum: active/completed/dropped, review_flag). `customer_code` (e.g. CUST-001) is auto-generated by the database on insert — don't try to set it yourself.
- `classes`: one row per class instance, linked to `customer_id`, with `status` enum (scheduled/done/not_completed/cancelled), `class_date`, `start_time`/`end_time`, `notes`.
- `payments`: one row per payment received, linked to `customer_id` (and optionally `class_id`), with `amount`, `payment_mode` enum (cash/upi/card/netbank/other).
- **`customer_summary` is a view, not a table** — it computes classes_completed, classes_remaining, amount_paid, amount_pending, and payment_status live from `classes` and `payments`. Read from this view for all dashboard/list/detail displays instead of computing these numbers client-side or duplicating them — this is intentional so the numbers can never drift out of sync.

**Functional requirements per screen (map these onto the fetched Stitch designs — don't add anything beyond what's listed):**

1. **Dashboard** — KPI cards (Total Enrolled, Active, Classes Left Today, Fee Pending) pulled from `customer_summary` and today's `classes`; today's class list with quick "Mark Done" actions.
2. **Attendance Log** — date-navigable list of `classes` rows for the selected date, each with a large "Mark Done" button that updates `status` to 'done'; an "Add Unscheduled Class" action to insert a new row.
3. **Enrolled Customers** — searchable/filterable list reading from `customer_summary` (filters: classes_completed range, enrollment_month, payment_status, course_status), "+ Add Customer" action that inserts into `customers`.
4. **Customer Detail** — pulls one row from `customer_summary` plus the full `classes` and `payments` history for that customer_id; actions to log a new class or record a new payment.
